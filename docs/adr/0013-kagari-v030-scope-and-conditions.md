# ADR-0013: KAGARI v0.3.0 の範囲と、RC から GA までの条件

- **Status:** Proposed（2026-11-26。PR の merge による User の承認で Accepted にする）
- **Human decision:** 2026-11-26 に User が次の方針を決めた：次のリリースは v0.3.0 とし、v0.3.0-rc.1 から v0.3.0（GA）へ進める。条件は、ADR で、User が承認する。MUSUBI のリリースは、固まるまで保留する。
- **Issue:** #556（この ADR）、#496（Epic）
- **Related:** ADR-0001（タグとリリースは User）、ADR-0009 D4（v0.2.0 の条件。変えない）、ADR-0010 D2・D5・D7、ADR-0011、ADR-0012
- **Amends:** ADR-0010 D7 の表の、許可台帳（#430）の時期「v0.2.x」：v0.3.0 に含める形に改める。ADR-0010 D2-3 の「台帳で決まらない操作は、止めずに人間の回答を待つ」：待機と Ask の公開（#430 の段階 2）は v0.3.0 に含めず、台帳に一致しない操作は、v0.3.0 では、拒否して `blocked` にし、拒否した操作と、登録できる許可の候補を、コメントに書く（#430 の段階 1 の実装のとおり）。ADR-0010 D5・D7 の「#436・#433 は v0.3 系の候補」は、変えない（v0.3.0 に含めないことは、「候補」と矛盾しない。D3）。

## Context

- v0.2.0（GA）は 2026-11-19（rc.1〜rc.3 の後）。それ以降、main には 34 の PR（#491〜#554 の範囲。`v0.2.0` から `main` までの merge commit の数）が入った。
- 主な変更：標準の導入の単位が、リポジトリからホストに変わった（ADR-0012：`install`・`status`・`uninstall`・`repair`・`reinstall`・`register`・`unregister`、取り込み）。許可台帳（ADR-0010 D2 の段階 1）と、許可の判定の強化。委任する判断の宣言と、独立レビューの `DELEGATION` の判定（HDC R1）。`work-once`（1 件が Ready になるまでの時間が、約 11 分から約 40 秒に短くなった）。止まった理由の分類と、孤立したブランチの片付け。
- ADR-0010 D7 は、許可台帳を「v0.2.x」としていた。実際には、導入の単位の変更と一緒に入るため、パッチの版（v0.2.1）では、変更の大きさを、利用者に伝えられない。

## Decision

### D1 — 次のリリースは v0.3.0（rc.1 → GA）
- 版は v0.3.0 とする。まず v0.3.0-rc.1 を出し、必要なら rc.2 以降を出して、GA（v0.3.0）に進む。
- タグとリリースは、ADR-0001 に従って User が行う。リリースノートは、v0.2.0 と同じ形（入っているもの／確認したこと／運用上の注意／未確認／既知の限界）で書く。確認したことと、未確認のことを分ける。

### D2 — v0.3.0（GA）の条件
次のすべてを満たしたときに、GA にする。確認済みの項目の記録は、Epic #496 のコメント（実機の確認の結果。日付・ホスト・内容）に残す（2026-11-26 に追記する）。
1. **ホスト単位の導入：** `install`・`status`・`uninstall`・`repair`・`reinstall`・`register`・`unregister`・取り込みが、実機で動いている（2026-11-24 までに、`kagari-host-test` で確認済み）。
2. **`work-once`：** 承認済みの 2 件が、1 回の実行で `reviewed` まで進む（2026-11-24 に確認済み）。
3. **許可台帳：** 実際の Claude Code で、hook が呼ばれ、許可・拒否・fail closed が働く（確認済み）。`ledger add`・`revoke`・`list` の CLI が、実機で動く（2026-11-26 に確認済み）。
4. **HDC R1：** 実機で、委任の宣言のある Issue について、PR が固定した選択を変えたとき、`DELEGATION` が `OUT` になり、PR が Draft のままになる。（未確認。RC の前に確かめる）
5. **分類：** 実機で、`blocked` のコメントに、分類（`[kind]`）と `Next:` が付く。エージェントが `BLOCKED: HUMAN_DECISION:` と宣言し、Draft PR が作られた場合も、`HUMAN_DECISION` になる（#550、#555）。（未確認。RC の前に確かめる）
6. **孤立したブランチの片付け：** 実機で、PR のない runner のブランチが、再実行の前に片付けられる（#551）。（未確認。RC の前に確かめる）
7. **運用：** 最後に公開した rc のタグ（rc.1、rc を出し直したら、その rc）から 72 時間、timer での運用が続き、その間に、承認済みの Issue を 5 件以上処理し、**手作業の復旧が 1 回も無い**。復旧とみなす作業は、ホストへの SSH での、状態を変える操作（`systemctl restart`・`reinstall`・ブランチや作業ディレクトリの手での削除・ファイルの編集）。承認ラベルの付与・外し、Issue 本文の修正、merge は、通常の運用で、復旧に数えない。期限の前に、あらかじめ計画した再ログイン（`kagari-mvi`〔30002〕のログインの期限は 2026-12-09 05:01 UTC。ADR-0009 追補 2026-11-18 の運用に従う）は、復旧に数えない。その間に出た `blocked` は、すべて分類されている。
8. **文書：** `components/kagari-mvi/README.md` について、次の 4 点を確かめる：(a) 「ホストのセットアップ」と標準の操作（`install`・`status`・`uninstall`・`repair`・`reinstall`・`register`・`unregister`・取り込み）の節が、現状と合っている。(b) 「対象リポジトリの道具」と「Nix を使う対象リポジトリ」の小節がある。(c) 既知の限界の節に、v0.3.0 に含めないもの（D3：並列、台帳の待機と Ask の公開）が書かれている。(d) 同じ項目の重複（例：「他のホスト」の 2 行）が無い。未確認の項目は、確認済みにするか、既知の限界として、リリースノートに明記する。

### D3 — v0.3.0 に含めないもの
- 同時に処理する Issue を 2 件以上にすること（#436。`work-once` で、待ち時間は、すでに短くなった）。
- 台帳に一致しない操作での、人間の回答の待機と、Ask の公開（#430 の段階 2。MUSUBI の #38 が依存する）。
- Pi による編集の実行役（#433）、NixOS の module（#504）、OAuth の期限が切れたときの実際の挙動の確認（30002 の期限は 2026-12-09）。
- MUSUBI のリリース（別の判断。固まるまで保留）。

### D4 — RC の前に済ませること
D2 の 4・5・6 の実機の確認と、#555（`BLOCKED` の宣言が Draft PR の経路で分類されない件）の修正。README の重複（D2-8 の (d)）の修正。

## Consequences
- ADR-0010 の Status に、この ADR で D7 の時期を改めたことを書く。`docs/adr/README.md` に、この ADR の行を足す。
- v0.2.0 の条件（ADR-0009 D4）は、変えない。
- D2 の 4〜6 が、実機で満たせない場合は、その項目を、既知の限界として書いて、GA の条件から外すかを、User が改めて決める。
