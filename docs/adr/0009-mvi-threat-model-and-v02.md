# ADR-0009: MVI の脅威モデルを「届く先」で決め、KAGARI v0.2 系を MVI で出す

- **Status:** Accepted（2026-11-13、User 判断）
- **Human decision:** 2026-11-13 に、User が次のことを承認した。
  - 脅威モデルは案A とし、届く先で判断する形で確定する。
  - Claude の資格情報は守る範囲に入れない。
  - v0.1 系の資産の扱いは、現状（ADR-0008 D2）を維持する。
  - 次のリリースは MVI を v0.2 系とする。あわせて、v0.2.0 の条件、ADR-0006 D6・D7-3 の先送りによる結果、#337 の扱いを決める。
- **Issue:** #420
- **Related:** ADR-0001（#1、#6）、ADR-0003（原則 3、原則 5）、ADR-0006（D6、D7-3、D8、Consequences）、ADR-0007（D3、D4、D7、Known limitations）、ADR-0008（D1、D2、D4、Consequences）、#337、#418
- **Amends:**
  - ADR-0001 #1：守る範囲に、外部からの入力による誘導を加える。
  - ADR-0006 D8：次のリリースの定義と、#291 の受入条件の表を、この ADR の D3 で置き換える。リリース範囲外の一覧は、v0.2 系では使わない。
  - ADR-0008 Consequences：ADR-0006 D6・D7-3 は「次のリリースを定義する ADR で決め直す」としていた。これを、D3 のとおり先送りに変える。

## Context
- ADR-0001 #1 は、守る範囲を「通常のミスや意図しない変更」に限っていた。悪意ある Agent への頑強性は保証しない、とも書いている。
- MVI（ADR-0007）では、public リポジトリの Issue 本文が Claude に渡りうる（D4）。独立レビューの指摘に応えるうちに、意図的な仕掛けを想定した対策が積み上がった。ところが、どこまでを守るかは決めていなかった。そのため、ADR-0003 原則 3（障害のたびに関門を増やさない）と食い違い始めていた。
- 「誘導された行為は守り、agent 自身の悪意は範囲外」という意図での分け方では、指摘を分類できない。Issue 本文を使えば、どの行為も誘導できるうえ、意図は外から観測できないためである。

## Decision

### D1 — 守る範囲は「届く先」で決める
1. **守る範囲**：次の (a)〜(c) のどれかに届く行為を防ぐ。原因はミスでも、外部からの入力（第三者が書いた Issue 本文やコメント、対象リポジトリの内容、依存パッケージ）による誘導でもよい。
   - (a) **GitHub の資格情報**。境界は OS のユーザー分離（ADR-0007 D3）とする。runner が commit すること（ADR-0007 D7）は、ここに入る対策である。git のフックを通じて、資格情報を持った状態でコードが動くのを防ぐ。
   - (b) **Contract の範囲の外**。`run-once --permission contract` を指定したときだけ、#418 の権限窓口で防ぐ。既定の `broad` では Contract と照合しないので、守るのは (a) と (c) だけになる。
   - (c) **人間の判断が要る操作**（merge、承認ラベル、タグ、リリース、履歴の破棄）。GitHub と git は runner が担い、`kagari-agent` は資格情報を持たない。#418 の窓口は、これらの操作を拒否したうえで、blocked にする信号を残す。
2. **範囲外**：(a)〜(c) のどれにも届かない行為。User が判断材料にする記録やレビュー結果を欺くだけのものを指す。例は次のとおり。
   - テストの再実行結果のすり替え
   - 権限窓口の判定記録の改ざん、偽の記録の書き込み
   - レビュアーの起動の乗っ取り
   - Claude の資格情報（`kagari-agent` の OAuth）の流出。これは守る範囲に入れない（User 判断）。
   - root やホストの侵害も、範囲外とする。
3. **範囲外の対策のうち、実装済みのもの**：次の対策は残す。ただし、同じ種類の対策を新しく足すことはせず、新しい指摘は既知の限界として記録する。
   - テストの再実行で行う、すり替え対策（プロセスを止める、`.verify` に checkout する、HOME を使い捨てにする、ログインシェルを使わない）
   - 権限窓口の記録を `O_NOFOLLOW` で作ること
4. **判断の基準**：新しい指摘や対策は、「(a)〜(c) のどれかに届くか」だけで分類する。
   - 届くなら、守る範囲として直す。
   - 届かないなら、ADR-0001 #6 と ADR-0003 原則 3 に従って対策を足さず、既知の限界に書く。

### D2 — v0.1 系の資産の扱い
- ADR-0008 D2 を維持する。Evidence、Recovery、metadata、dispatch 経路の部品は、必要が示されたときだけ取り込む。

### D3 — KAGARI v0.2 系は MVI で出す
- 次のリリースは、`components/kagari-mvi/` を中心とする KAGARI v0.2 系とする。ADR-0006 D8 のリリース定義と、#291 の受入条件の表は使わない。
- **v0.2.0 の条件**（User 承認）：
  1. ADR-0008 D4 の前提条件を満たす。
     - Contract 権限窓口（#418）
     - GitHub Actions の secrets への対策
     - dispatch 経路を削除するかの判断
     - ADR-0007 に残った課題を、KUMIKI の前に決めるかどうかの判断
     - レビュアーの起動の乗っ取りは、D1-2 で範囲外と決まったので、判断済みとする。
  2. レビュー担当を OpenCode と TSUMGI に切り替えられる（ADR-0007 D6 の 2 周目）。
  3. KUMIKI 自身を対象にして、E2E を一周させる。
  4. systemd timer で動かす手順を README に書く。
- **ADR-0006 D6・D7-3 の先送りによる結果**：v0.2 系では、この 2 つを扱わない。その結果、次のようになる。
  - v0.2 系で同時に処理する Issue は 1 件のままとする。
  - v3 からの移行を始める条件が無くなる。v3 の保守の凍結（ADR-0006 D7）は、別の ADR で決め直すまで続く。
  - ADR-0006 Consequences にある #337 の「リリースまで止める」は、下の「#337 の扱い」に置き換える。
- **#337（Metadata v2）の扱い**：#337 は dispatch 経路の metadata を作り直すものである。目的は、同時実行のときに書き込みが衝突しないことと、Task の記録を長く保つことにある。一方、MVI は metadata を使わず、状態をラベルだけで持つ。このため、次のように扱う。
  - **決める時期**：v0.2.0 を出す前に決める。上の条件 1 で dispatch 経路を削除するかを判断するとき、あわせて #337 を close するか、作り直して再開するかを決める。
  - **再開する条件**：次のどちらかが示されたときに限り、MVI 向けに範囲を絞り直して起票する。
    - 同時に処理する Issue を 2 件以上にする必要が出たとき
    - Task の記録を GitHub 上に長く残す必要が出たとき（ADR-0008 D2 の「必要が示されたとき」にあたる）
  - **再開の目安**：早くても v0.2.0 の後で、v0.3 系の候補とする。v0.2 系では作業を再開しない。
- タグの作成とリリースは、ADR-0001 に従って User が行う。

本 ADR は、Merge、Release、本番適用を承認するものではない。
