# ADR-0011: 人間のレビューは、ロジックを置く場所の判断に絞る

- **Status:** Accepted（2026-11-16、PR #451 の merge による User の承認）。追補 2026-11-17（#452、全体ロジック・置く理由・却下した置き場所を Issue に書く）、追補 2026-11-17 の 2 件目（#462、承認依頼に当初の目的と目的とのずれを必須にし、CI の通過は書かない。項目を 8 つにして順序を改める）
- **Human decision:** 2026-11-16 に User が次の方針を決めた。コードとロジック自体の正しさはテストで保証し、そのロジックをその場所に入れることの正しさは人間が判断する。承認依頼の 4 点（ADR-0006 D5）を、この判断に必要な項目に置き換える。
- **Issue:** #450
- **Related:** ADR-0006（D5）、ADR-0007（D1 の手順 6）、ADR-0008（D5）、ADR-0010（D3）
- **Amends:**
  - ADR-0006 D5：承認依頼の 4 点（5 行以内の要約・差分行数・人間が読むべきファイル・却下した場合の影響）を、D2 の項目に置き換える。「欠けている依頼は中身を見ずに差し戻す」は残す。
  - ADR-0007 D1 の手順 6 と ADR-0008 D5：「承認依頼の 4 点」は D2 の項目と読み替える。
  - 追補 2026-11-17 の 2 件目（#462）：D2 の項目を新しい 8 項目に置き換え、D3 の対象をその 8 項目にする（追補の表を参照）。

## Context
- 4 点の承認依頼は、人間がコードを読んで正しさを確かめることを前提にしていた（「人間が読むべきファイル」）。
- ADR-0010 D3 で、独立レビューがすべて PASS で、テストの再実行も通ったときだけ Ready にすることになった。ロジックの正しさは、テストと独立レビューで確かめる仕組みができている。
- テストと独立レビューでは確かめられないのは、そのロジックをその場所に入れるのが正しいか、である。これは全体の設計を知っている人間が判断する。
- テストを書くのは実装したエージェント自身である。テストが何を保証していて、何を保証していないかが承認依頼に書かれていないと、人間は保証があるものと思い込んだまま置き場所を判断することになる。

## Decision

### D1 — 役割の分担
- **コードとロジック自体の正しさ**：テストで保証する。独立レビューは受入条件ごとに PASS/FAIL を判定し、すべて PASS でテストの再実行も通ったときだけ Ready にする（ADR-0007 D1 の手順 5、ADR-0010 D3）。
- **そのロジックをその場所に入れることの正しさ**：人間が判断する。人間がコードを読むことは前提にしない。

### D2 — 承認依頼の項目
> **追補 2026-11-17 の 2 件目（#462）で、この項目は新しい 8 項目に置き換えた。新旧の番号の対応は、末尾の追補の表を参照。以下は、置き換え前の 6 項目の原文。**

承認依頼は、Adam 上で User と対話している設計用の Claude Code のセッション（ADR-0008 D5）が、PR とレビューを読んでまとめる。次の順で書く。

1. **関係する全体ロジックの概要**：変更が入る処理の流れ全体。入口から出口まで、どのコンポーネントを通るか。
2. **ロジックの概要**：追加・変更したロジックが何をするか。
3. **ここに入れる理由**：なぜこの場所に入れたか。
4. **テストの保証範囲**：
   - テストごとに、何を保証することを目的にしているかを 1 行で説明する。対応する受入条件も示す。
   - テストで確かめていないことを書く。無ければ「無し」と書く。
5. **却下した置き場所**：検討した他の候補と、却下した理由を 1 行ずつ。比較できる程度に簡単に書く。
6. **補足：却下した場合の影響**を 1 行。

差分行数と「人間が読むべきファイル」は書かない。PR へのリンクは付ける。

### D3 — 欠けている依頼
> **追補 2026-11-17 の 2 件目（#462）で、対象は新しい 8 項目になった。以下は原文。**

D2 の 1〜6 のどれかが欠けている依頼は、中身を見ずに差し戻す（ADR-0006 D5 の規則を引き継ぐ）。

## Consequences
- 人間は置き場所の判断に集中できる。その代わり、ロジックの正しさはテストの質に依存する。D2 の 4 で、テストが保証していない範囲を人間が見えるようにする。
- 承認依頼をまとめる設計用セッションは、全体ロジックと却下した候補を説明できる程度に、変更の周辺を読む必要がある。
- 承認依頼を生成するコードは、現時点で存在しない（設計用セッションが手で書いている）。KAGARI に承認依頼の生成を入れるときは、D2 の項目を使う。

## 追補（2026-11-17、#452、User 判断 2026-11-16 の案 B）
- D2 の 1（関係する全体ロジックの概要）・3（ここに入れる理由）・5（却下した置き場所）は、**Issue に書く**。User は承認ラベルを付ける時点で、これらを読んで置き場所を判断する。実装の後に、置き場所の判断材料を推測で書くことを防ぐためである。
- Issue の見出しは `### 全体ロジック`・`### 置く理由`・`### 却下した置き場所`（英語では `### Overall logic`・`### Why here`・`### Rejected placements`）とする。候補が無い場合は「無し」と、その理由を 1 行書く。
- `kagari-mvi` の `run-once` は、どれかの見出しが無いか中身が空の Issue を、Claude を起動する前に `blocked` にし、欠けている見出しをコメントする。中身の良し悪しは判定しない。
- PR の承認依頼では、D2 の 1・3・5 を Issue から引き写し、実装が Issue から外れた点があればそれを書く。2・4・6 は従来どおり PR で書く。

## 追補（2026-11-17 の 2 件目、#462、User 判断）
承認依頼で、PR の当初の目的と実際の実装が分からない、CI で確かめられる内容が多すぎる、という指摘への対応。D2・D3 と、上の追補（#452）の最後の項を改める。

- **項目を足す**：
  - **当初の目的**：Issue が何を達成するため、何を防ぐためのものだったか（1〜2 行）。Issue の「防ぐ誤り」と要件から引き写す。
  - **目的とのずれ**：必須の項目にする。足したもの、やらなかったもの、指示が無く実装側の判断で決めたものを書く。無ければ「無し」と書く（書き忘れと「ずれが無い」を区別するため）。上の追補（#452）の「実装が Issue から外れた点があればそれを書く」（任意）は、この項で置き換える。
- **書かないこと**：CI・テスト・独立レビューが通ったことは書かない。失敗、未実施、判定不能のときだけ書く（CI の結果は GitHub 上で確かめられ、判断の材料にならないため）。テストの件数と行数も書かない。詳細は PR・Issue・レビューのコメントへのリンクで示す。
- **項目の順序と番号**：決めることに近いものを先にする。D2 の項目を、次の新しい 8 項目に置き換える（旧 D2 の「関係する全体ロジックの概要」「ここに入れる理由」「却下した置き場所」を、別々の項目として数える）。

  | 新 D2 | 項目 | 旧 D2 | 出どころ |
  | --- | --- | --- | --- |
  | 1 | 当初の目的 | （新設） | Issue の「防ぐ誤り」と要件 |
  | 2 | ロジックの概要（実際の実装） | 2 | PR |
  | 3 | 目的とのずれ | （新設） | PR（無ければ「無し」） |
  | 4 | 関係する全体ロジックの概要 | 1 | Issue から引き写す |
  | 5 | ここに入れる理由 | 3 | Issue から引き写す |
  | 6 | 却下した置き場所 | 5 | Issue から引き写す |
  | 7 | テストの保証範囲 | 4 | PR（テストごとの目的と、確かめていないこと） |
  | 8 | 却下した場合の影響 | 6 | Issue の「防ぐ誤り」 |

  ADR のほかの箇所の「D2 の n」は、この表で読み替える。上の追補（#452）の「D2 の 1・3・5 は Issue から引き写し」は新 D2 の 4・5・6、「2・4・6 は従来どおり PR で書く」は新 D2 の 2・7・8（1 と 3 は、Issue と PR から作る）、Consequences の「D2 の 4」（テストの保証範囲）は新 D2 の 7 のことである。
- **D3（欠けている依頼）**：差し戻しの対象を、新 D2 の 8 項目すべてにする（当初の目的と目的とのずれを含む）。どれかが欠けている依頼は、中身を見ずに差し戻す。
- **変えないこと**：判断の枠組み（正しさはテストと独立レビュー、置き場所は人間）、承認依頼を設計用セッションがまとめること、#453 のテストの目的の申告。新 D2 の 7（テストの保証範囲）で、テストごとの目的と、テストで確かめていないことを書く点も変わらない。KAGARI が承認依頼を生成するとき（#476）は、この項目と順序を使う。生成できるようになった後の設計用セッションの役割は、#476 で決める。
- Adam の設計用セッションの指示ファイルと、暫定運用の指示書は、この ADR の merge の後に User が書き換える。
