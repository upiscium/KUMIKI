# ADR-0009: KAGARI の責任範囲を決め、KAGARI v0.2 系を MVI で出す

- **Status:** Accepted（2026-11-13、User 判断）
- **Human decision:** 2026-11-13 に、User が次のことを承認した。
  - KAGARI の目的は「簡単かつ安全に Agent 開発をすること」とし、攻撃への防御は目的にしない。責任を持つ範囲と持たない範囲を D1 のとおりとする。
  - Contract と照合する権限窓口（#418 の当初の設計、Draft PR #419）は作らず、push の前に保護するファイルの変更を確かめる軽い仕組みに置き換える。
  - 承認した後の Issue 本文の変更を検知する仕組みを、v0.2.0 の条件に加える。
  - GA の実行環境は、OS のユーザー分離だけを前提とする。LXC は MVI の実機確認に限った環境とする。
  - v0.1 系の資産の扱いは、現状（ADR-0008 D2）を維持する。
  - 次のリリースは MVI を v0.2 系とする。あわせて、v0.2.0 の条件、ADR-0006 D6・D7-3 の先送りによる結果、#337・#391 の扱いを決める。
- **Issue:** #420
- **Related:** ADR-0001（#1、#6）、ADR-0003（原則 3）、ADR-0006（D6、D7-3、D8、Consequences）、ADR-0007（D3、D7、Known limitations）、ADR-0008（D2、D4、Consequences）、#337、#391、#418、#419、#422
- **Amends:**
  - ADR-0006 D8：次のリリースの定義と、#291 の受入条件の表を、この ADR の D4 で置き換える。リリース範囲外の一覧は、v0.2 系では使わない。
  - ADR-0006 D7-3 と Consequences（#337 の行）：D4 のとおりに変える。
  - ADR-0007 D3：「実行場所は専用 LXC」を、MVI の実機確認に限った決定とする（D2）。権限窓口を作らない、という判断は維持する。
  - ADR-0008 D3 の W2 の行：Contract 権限窓口は取り込まない。#394 と Draft PR #402 は、取り込み用の Issue を待たずに close する。
  - ADR-0008 D4：KUMIKI 自身を対象にする前の前提条件を、D4 の条件 1 で置き換える。
  - ADR-0008 Consequences：ADR-0006 D6・D7-3 は「次のリリースを定義する ADR で決め直す」としていた。これを、D4 のとおり先送りに変える。

## Context
- ADR-0001 #1 は、保証する安全性を「通常のミスや意図しない変更の抑制」とし、悪意ある Agent への頑強性は保証しない、としている。
- MVI（ADR-0007）では、public リポジトリの Issue 本文が Claude への指示になる。独立レビューで抜け道を探すたびに対策を足した結果、#418 の権限窓口は約 380 行になり、なお抜け道が見つかり続けた。KAGARI が攻撃への防御システムに寄り始め、ADR-0003 原則 3（障害のたびに関門を増やさない）とも食い違っていた。
- 原因は、KAGARI が何に責任を持つのかを決めていなかったことにある。

## Decision

### D1 — KAGARI の責任範囲
1. **目的**：KAGARI は、簡単かつ安全に Agent 開発をするためのシステムである。ここでの「安全」は、agent の誤りで取り返しのつかないことが起きないこと、人間が決めるべきことを agent が勝手に決めないことを指す。
2. **責任を持つもの**：
   - **人間の判断の関門**：承認ラベル `kagari:approved` を付けるのは User だけとし、merge、Ready 化、タグ、リリースは人間が行う。承認したときと違う Issue 本文では動かない（D4 の条件 1）。
   - **GitHub の資格情報の分離**：agent は GitHub の資格情報を持たない。commit、push、PR、ラベルの操作は runner が行う（ADR-0007 D3・D7）。
   - **誤操作の防止**：保護するファイル（リポジトリのどの階層にある指示ファイルと `.claude/`、および `.github/workflows/`）の変更は、push の前に runner が見つけて止め、`kagari:blocked` にして人間の判断に回す。正確な一覧と、Issue で変更を許す方法は #418 で決める。Claude の設定の拒否ルールで、うっかりの書き換えも減らす。
   - **検証**：runner によるテストの再実行と、独立レビュー。これらは誤りを見つける仕組みであり、この ADR で狭めない。
3. **責任を持たないもの**：
   - プロンプトインジェクション、悪意ある入力や agent への防御。Issue の中身が安全かどうかは、承認する人間が判断する。
   - 記録やレビューを欺く行為（テスト結果のすり替え、記録の改ざん、レビュアーの起動の乗っ取りなど）、Claude の資格情報（`kagari-agent` の OAuth）の流出、root やホストの侵害。
   - 対象リポジトリの設定による危険。たとえば、push したコードを GitHub Actions が secrets 付きで実行すること。KAGARI は防がず、README で注意する。
4. **実装済みの対策の扱い**：テストの再実行で行う対策（プロセスを止める、`.verify` に checkout する、HOME を使い捨てにする、ログインシェルを使わない）は、再現性を保つ役にも立つので残す。同じ種類の対策を新しく足すことはしない。
5. **判断の基準**：新しい指摘は、「通常の使い方や誤操作で、2 の責任が破れるか」で分類する。
   - 破れるなら、直す。
   - 攻撃者が意図して作る経路でしか破れないなら、対策を足さず、既知の限界として README に書く（ADR-0001 #1・#6、ADR-0003 原則 3）。
   - 独立レビューにも、この基準で確かめさせる。攻撃者として抜け道を探すことは求めない。

### D2 — 実行環境の前提
- GA の実行環境は、同じホスト上の OS のユーザー分離（`kagari-runner` と `kagari-agent`）だけを前提とする。2 つのユーザーは KAGARI 専用とする。
- ADR-0007 D3 で LXC が担っていた役割（権限窓口を作らない代わりの境界）は、OS のユーザー分離と、Claude の起動設定の拒否ルール（ADR-0007 D7）が担う。
- LXC は、MVI の実機確認に使った環境である。手順や README では、LXC を必須の前提として書かない。ADR-0007 D3 の「Adam では動かさない」も、MVI の実機確認に限った決定とする。

### D3 — v0.1 系の資産の扱い
- ADR-0008 D2 を維持する。Evidence、Recovery、metadata、dispatch 経路の部品は、必要が示されたときだけ取り込む。

### D4 — KAGARI v0.2 系は MVI で出す
- 次のリリースは、`components/kagari-mvi/` を中心とする KAGARI v0.2 系とする。ADR-0006 D8 のリリース定義と、#291 の受入条件の表は使わない。
- **v0.2.0 の条件**（User 承認）：
  1. KUMIKI 自身を対象にする前提条件（ADR-0008 D4 を置き換える）を満たす。
     - 保護するファイルの変更を、push の前に止める（#418）。Contract と照合する権限窓口は作らない。
     - 承認した後に Issue 本文が変わったら、実行せずに止める（#422）。
     - GitHub Actions の secrets の危険を README に書く。
     - dispatch 経路を削除するかを判断する。あわせて #337・#391 の扱いを決める（下記）。
     - OAuth を長く使い続けられるか（ADR-0007 Known limitations）と、再起動したときに同じ Issue を二重に取得しないこと（ADR-0007 Acceptance evidence、一部確認）を、KUMIKI の前に確かめるかを判断する。
     - ADR-0008 D4 にあったレビュアーの起動の乗っ取りと、Bash による Claude の資格情報の流出は、D1-3 で責任の外と決まったので、判断済みとする。
  2. レビュー担当を OpenCode と TSUMGI に切り替えられる（ADR-0007 D6 の 2 周目）。
  3. KUMIKI 自身を対象にして、E2E を一周させる。
  4. ユーザー分離だけで動かす手順と、systemd timer で動かす手順を README に書く。
- **ADR-0006 D6・D7-3 の先送りによる結果**：v0.2 系では、この 2 つを扱わない。その結果、次のようになる。
  - v0.2 系で同時に処理する Issue は 1 件のままとする。
  - v3 からの移行を始める条件が無くなる。v3 の保守の凍結（ADR-0006 D7）は、別の ADR で決め直すまで続く。
  - ADR-0006 Consequences にある #337 の「リリースまで止める」は、下の「#337・#391 の扱い」に置き換える。
- **#337（Metadata v2）・#391 の扱い**：#337 は dispatch 経路の metadata を作り直すものである。目的は、同時実行のときに書き込みが衝突しないことと、Task の記録を長く保つことにある。一方、MVI は metadata を使わず、状態をラベルだけで持つ。#391 は #337 と一緒に止めていたので、同じく扱う。
  - **決める時期**：v0.2.0 を出す前に決める。上の条件 1 で dispatch 経路を削除するかを判断するとき、あわせて close するか、v0.3 系の候補として残すかを決める。
  - **再開する条件**：次のどちらかが示されたときに限り、MVI 向けに範囲を絞り直して起票する。
    - 同時に処理する Issue を 2 件以上にする必要が出たとき
    - Task の記録を GitHub 上に長く残す必要が出たとき（ADR-0008 D2 の「必要が示されたとき」にあたる）
  - **再開の目安**：早くても v0.2.0 の後で、v0.3 系の候補とする。v0.2 系では作業を再開しない。
- タグの作成とリリースは、ADR-0001 に従って User が行う。

## Consequences
- #418 の本文を、保護するファイルの確認に書き換える。Draft PR #419 は merge せずに閉じる。
- `run-once --permission contract` は作らない。Claude の起動は、今の 1 種類のままとする。

本 ADR は、Merge、Release、本番適用を承認するものではない。
