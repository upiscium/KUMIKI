# ADR-0010: 実行役を Claude Code と Pi に分け、許可台帳と運用ルールを足す

- **Status:** Accepted（2026-11-15、PR #439 の merge による User の承認）; 追補 2026-11-16（行数の上限を 1 ファイルあたり本体 500 行・テスト 800 行に変更、#454）; 追補 2026-11-22（D6・D7 の「MUSUBI が制御セッションを管理する」〔MUSUBI#39〕を、upiscium/MUSUBI#43 の決定に合わせて取り消し、#521）
- **Human decision:** 2026-11-14〜15 の設計セッションで、User が次の方針を決めた（#429、指示書「KAGARI/MUSUBI 次期方針 実装指示書」）。この ADR はそれを記録し、改定する ADR の箇所を示す。
- **Issue:** #429
- **Related:** ADR-0006（D1、D3、D4、D6）、ADR-0007（D2、D3、D4、D7）、ADR-0009（D1、D4、Consequences、追補 2026-11-14）、#340、#359、#418、#419、#427、#430〜#437、upiscium/MUSUBI#37〜#39
- **Amends:**
  - ADR-0006 D1：本流の実行役は Claude Code のまま。Leaf の実行役を OpenCode から Pi（ローカルモデル専用）に替え、OpenCode の対応を終える（D1）。
  - ADR-0006 D3：独立レビューなど編集を伴わない Leaf は、エージェントの仕組みを挟まず TSUMGI の API を直接呼ぶ。編集する Leaf は Pi で動かす（D1）。
  - ADR-0006 D4：権限 Ask を、Contract との照合ではなく、許可台帳で判定する。台帳で決まらない操作は、拒否せずに人間の回答を待つ（D2）。
  - ADR-0006 D6：同時に処理する Issue を 2 件以上にすることを、v0.3 系の候補にする。metadata v2（#337）への移行という前提は外す（D5）。
  - ADR-0007 D3・D7：「権限窓口は MVI では作らない」と、Claude を `--permission-prompts none` で起動することを改め、許可台帳を参照する判定に変える（D2）。
  - ADR-0009 D1-2：Ready 化を、独立レビューがすべて PASS で、テストの再実行も通ったときに限って runner が行う。merge、タグ、リリースは人間だけが行う（D3）。
  - ADR-0009 D4 条件 2：「レビュー担当を OpenCode と TSUMGI に切り替える」を「TSUMGI の直接呼び出しに切り替える」と読み替える（ADR-0009 追補 2026-11-14 と同じ。D1）。
  - ADR-0009 D4 条件 1 と Consequences：「Contract と照合する権限窓口は作らない」「`run-once --permission contract` は作らない。Claude の起動は、今の 1 種類のまま」を改め、範囲を絞った許可台帳を作る（D2）。Contract との照合には戻さない。

## Context
- OpenCode は不要な機能が多い。指示文と tool の定義だけで約 9,000 トークンになり、TSUMGI の入力の上限（10,240 トークン）を超える（#427 で観測）。
- ADR-0009 で権限窓口をやめた結果、台帳に相当するものが無い。人間が一度許した同じ操作（例：特定のホストへの `ssh`）も、Issue のたびに拒否され、`blocked` になる。
- 拒否して `blocked` にすると、再実行は新しいセッションで最初からやり直しになり、それまでの作業のトークンを使い直す。
- 承認済みの方針と、それに食い違う実装が、別々の Issue で進むおそれがある。

## Decision

### D1 — 実行役
- **本流**：Claude Code（クラウドモデル）。
- **編集する Leaf**：Pi（https://pi.dev/）。ローカルモデル専用とし、`kagari-agent` ユーザーで動かす（#433、v0.3 候補）。
- **編集を伴わない Leaf**（レビュー、要約、分類）：TSUMGI の OpenAI 互換 API を直接呼ぶ（#427 を一般化する。#434）。
- **OpenCode**：2.x 系には上げない。1.x 系も含めて、対応を終える（#435）。v0.1.0 として公開済みの成果物は書き換えない。

### D2 — 許可台帳
1. **目的**：人間が一度「この範囲で常に許可」と答えた操作を、以後は KAGARI が自動で許可する。目的は、同じ許可を何度も聞かないことと、誤操作の防止に限る。**攻撃への防御は目的にしない**（ADR-0009 D1）。抜け道が見つかるたびに条件を足すことはしない（#418 の失敗を繰り返さない）。
2. **台帳**：`kagari-runner` だけが書ける場所に置き、agent は読み書きできない。1 件の許可は、操作の種類、照合の条件、有効範囲（Issue / リポジトリ / ホスト全体）、期限、登録した日時と理由を持つ。既定の有効範囲は Issue とする（#430）。
3. **台帳で決まらない操作**：実行を止めずに、人間の回答を待つ（User 判断 2026-11-15）。
   - MUSUBI に Ask を出し、once / always（範囲と期限つき。台帳に登録する）/ 拒否 で答えてもらう（upiscium/MUSUBI#38）。
   - 待つ時間には上限を設ける。既定値は #430 で決める。時間切れなら拒否して `kagari:blocked` にし、回答の無かった操作と許可の候補を、1 件のコメントにまとめる。回答があった Ask はコメントしない。
   - **待っている時間は、agent の実行時間の上限（`AGENT_TIMEOUT`）に数えない。** 人間の応答の速さで、agent の作業時間を削らないためである。
   - 待っている Ask は、runner のプロセスが生きている間だけのものとする。プロセスが終われば消える。状態をラベルだけで持つ原則（ADR-0007 D2）は、永続する状態について保つ。
   - v0.2 系は 1 件ずつ処理するので、待っている間は他の Issue も止まる。README の既知の限界に書く。
4. **事前の許可**：Issue 本文の `### 追加で許可する操作` で宣言できる。承認ラベルを付けることで、その宣言も承認したことになる。範囲はその Issue だけとする（#431）。Claude に渡すのは本文だけで、コメントは読まない（ADR-0007 D4）。
5. **判定の仕組み**：Claude Code の起動を `--permission-prompts none` から、台帳を参照する判定に変える。PreToolUse hook と `--permission-prompt-tool` のどちらを使うかは、#430 で決める。
   - 2026-11-15 に LXC（Claude CLI 2.1.322、`kagari-agent`）で、どちらも回答を待てることを確かめた。判定を返す前に 300 秒と 1,500 秒待たせても、Claude は待ち続け、許可されたコマンドを実行した。
   - 違い：hook はすべての呼び出しで動き、hook ごとに `timeout`（既定 60 秒）を広げる必要がある。`--permission-prompt-tool` には、allow / deny のルールで決まらなかった操作だけが届く。
   - 1,500 秒より長く待てるかは、未確認である。確認の手順と結果は、PR #439 のコメントに残す。
6. **各実行役のネイティブな always は使わない。** 許可の状態は、KAGARI の台帳だけに置く。
7. **台帳に登録するのは人間だけ**とする。制御用の Claude セッション（設計・全体制御を行う LLM）は、KAGARI の許可に答えられない。

### D3 — Ready 化と運用ルール
- 独立レビューがすべての受入条件を PASS と判定し、runner によるテストの再実行も通ったときに限り、runner が Draft を Ready にする（#432）。FAIL か UNKNOWN が 1 つでもあれば、Draft のままにする。merge、タグ、リリースは引き続き人間だけが行う。
- すべての変更に、実装したセッションとは別のセッションが独立レビューを行う。
- merge の後、不要になったブランチと worktree を消す（#432）。

### D4 — 秘密情報を要するテスト
- deploy ブランチは作らない。merge してから revert する運用も使わない。
- 使い捨ての worktree にコミットを取り出し、秘密情報は実行時にホスト側（runner）で注入する。agent と Claude は秘密情報を読まない（#437）。注入元は #437 で決める。

### D5 — 並列化
- 同時に処理する Issue を 2 件以上にする（#436）。ADR-0009 D4 の再開条件「同時に処理する Issue を 2 件以上にする必要が出たとき」を満たしたものとし、v0.3 系の候補とする。ADR-0006 D6 の「metadata を v2 に移した後」という前提は外す。MVI は状態をラベルだけで持つためである。#337 は閉じたままとし、必要な部品は #436 で MVI 向けに起票し直す。

### D6 — 制御セッションと MUSUBI
- 設計と全体の制御は Claude のセッションで行う。当面は Remote Control で動かし（Phase A）、将来は MUSUBI が起動して管理する（Phase B。upiscium/MUSUBI#39）。KAGARI へは、Issue と承認ラベルで指示する。
  - **追補（2026-11-22、取り消し）：** 上の Phase B は upiscium/MUSUBI#43（Human 決定、2026-11-22）で取り消された。制御セッションは、当面も将来も Remote Control など MUSUBI の外の Claude セッションで行い、MUSUBI は制御セッションを管理しない。MUSUBI の役割は、KAGARI と GitHub の読み取り専用の参照、Discord 通知、人間の操作の中継だけである。Ask と許可台帳の権限は KAGARI が持つ。MUSUBI#43 は、旧 MUSUBI#39 と #429 の制御セッション統合の記述より優先する。
- MUSUBI は KAGARI MVI（GitHub のラベル）につなぎ、複数のリポジトリの `blocked` を集める（upiscium/MUSUBI#37）。今の `kagari-cli-adapter` と OpenCode 専用の分類器は凍結する。

### D7 — 実装の順序と v0.2.0 の範囲

## Consequences
- ADR-0006、ADR-0007、ADR-0009 の Status 行に、この ADR で一部を改定したことを書く。
- `kagari-mvi` の本体 2 ファイルは、合計 800 行以内を保つ。超える場合は別のファイルに分け、理由を PR に書く。（追補 2026-11-16 で、1 ファイルあたり本体 500 行・テスト 800 行に変更）

## 追補（2026-11-16、User 判断、#454）
- `kagari-mvi` の行数の上限を、「本体 2 ファイルで合計 800 行」から「**1 ファイルあたり、本体は 500 行、テスト（`test_*.py`）は 800 行**」に変える。
- 上限は `just mvi::test` のテスト（`LineLimitTest`）で確かめ、超えたらテストを失敗させる。
- 超える場合は、責任の単位でファイルを分け、理由を PR に書く。上限の数字は上げない（500 → 700 → 800 と上げてきた結果、上限が制約として働かなかったため）。
- 理由：ADR-0011 で人間がコードを読まないことにしたので、人間が読める大きさに保つ理由は無くなった。残る理由は、エージェントがファイルを丸ごと読むときのコンテキストの量と、責任範囲が膨らんでいないかの目安で、どちらも 1 ファイルの大きさで決まる。テストも丸ごと読まれるので上限を設けるが、ケースを並べる分だけ長くなりやすいため、本体より大きい値にする。
- 本体の値は ADR-0007 D5 の当初の目安と同じにした。2026-11-16 の時点で、本体の各ファイルは 426 行・366 行・91 行、テストは 608 行で、どれも上限に収まっている。

本 ADR は、Merge、Release、本番適用を承認するものではない。
